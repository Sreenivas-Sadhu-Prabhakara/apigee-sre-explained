1 · The SRE ladder

Site-reliability practice turns a vague goal ("the API should be up and fast") into measured, actionable signals. It builds in rungs, each one standing on the one below. Here is the whole ladder, as it was built for the bank-ai-demo proxy.

1

A dashboard of the golden signals

See rate, errors and latency per proxy, at a glance — the raw truth before any target is set.

2

Service-level objectives (SLOs)

Turn two of those signals into promises: how available, and how fast, the service should be over a window.

3

An error budget

The exact amount of failure the promise permits. 99.9% available is not "no failures" — it is a budget you can spend.

4

Burn-rate alerts

Page a human only when the budget is being spent too fast to last the window. Alert on risk, not on every blip.

2 · RED and the percentiles

RED is three questions you ask of any request-serving system. It is the fastest honest health read there is.

R — Rate
Requests per second. The workload. Measured from proxy/request_count with a rate aligner.
E — Errors
The fraction of responses that failed, not the raw count. A ratio of 5xx responses over all responses — a count alone hides whether 50 errors is a catastrophe or a rounding error.
D — Duration
How long requests take, read at percentiles — p90, p95, p99 — because an average hides the slow tail that users actually feel.

Why p90 is the awkward one

Cloud Monitoring can compute percentiles from a raw latency distribution, but its aligner only offers the 5th, 50th, 95th and 99th — there is no p90. Apigee rescues the request: it emits a pre-computed gauge, proxyv2/latencies_percentile, that already carries p50, p90, p95 and p99 over a rolling two-minute window. So the dashboard reads p90 straight from that gauge. Cloud Run has no equivalent, so its panel honestly shows p50/p95/p99 and says p90 is unavailable.

◆ the subtlety

This pre-computed gauge is also the reason for the finding in section 6. A two-minute windowed percentile and a full distribution are different mathematical objects, and they disagree when there is a tail.

3 · SLOs and the error budget

An SLO is a promise expressed as "X% of events are good over a rolling window." Two were set on bank-ai-demo, the one proxy with sustained traffic.

Availability
99.9% of requests are non-5xx, over a rolling 28 days. A good/total ratio.
Latency
99% of requests finish under 300 ms, over a rolling 28 days. A cut of the latency distribution.

4 · Burn-rate alerting

A flat "error rate > 2%" alert is a bad pager: it screams at a one-minute blip and sleeps through a slow leak. Burn-rate alerting asks a better question — at the current rate of spending, how fast is the budget running out? A burn rate of 1 means the budget lasts exactly the window. A burn rate of 14.4 means it will be gone in about two hours.

Two windows are watched at once, so fast disasters and slow erosion are both caught without false pages:

CRIT  availability FAST 14.4×/1h WARN  availability SLOW 6×/6h CRIT  latency FAST 14.4×/1h

5 · What was built

Every object is a JSON file applied through the Cloud Monitoring REST API by one idempotent script, in dependency order. Re-running patches in place rather than duplicating. Server-assigned IDs are captured to a local state file.

Channel
An email notification channel (owner address) — where the alerts page.
Service
apigee-bank-ai-demo-eval, a custom Monitoring service the SLOs hang off.
SLOs
availability-999 (good/total ratio, bad = response code 500–599) and latency-p99-300ms (distribution cut, 0–300 ms).
Alerts
Three burn-rate policies, all enabled and wired to the channel, deterministic names.
Dashboard
"Apigee SRE — RED + SLO (eval)", 11 widgets — scorecards, rate/errors/latency by proxy, the error-budget gauge, and a Cloud Run panel.

The availability SLI counts anything that is not a 5xx as good. The two latency metrics are chosen deliberately and never cross-wired: the dashboard percentile panels read the proxyv2/latencies_percentile gauge (the only source of p90), while the latency SLO reads the proxy/latencies distribution (a gauge cannot carry a good/total ratio or a distribution cut).

6 · The finding: a tail the dashboard hid

This is the part worth the whole exercise. On the dashboard, bank-ai-demo looks fast: p99 sits near 140 ms, comfortably under the 300 ms line. The latency SLO, reading the same proxy over the same day, disagreed — it reported only 92.7% of requests under 300 ms, against a 99% target, with three-quarters of its error budget already spent.

▲ why this matters, and that it is not a bug

A two-minute-window p99, averaged across a day, smooths out bursts of slow requests. The distribution the SLO reads does not — it is every request's latency, tail and all. The gap between "p99 ≈ 140 ms" and "only 92.7% under 300 ms" is exactly the backend tail an SLO exists to surface. Both metrics are wired correctly; the SLO simply sees what the panel cannot.

It is not currently breaching — the burn rate (~12.6) sits just under the fast-page threshold (14.4) — but the 300 ms target was chosen against the optimistic gauge reading. If 300 ms was meant to be comfortably met, widen the objective (for example 99% under 500 ms, or 95% under 300 ms) in the SLO file and re-apply.

7 · Operating it

The whole ladder is four commands. Everything is declarative, so the repo is the source of truth and the API is just where it is applied.

# create or update everything, in dependency order (idempotent)
bash scripts/apply.sh

# prove it against live GCP — runs every check, asserts the real shapes
bash tests/test_e2e.sh

# modest traffic so the idle-proxy panels render (not a load test)
bash scripts/seed-traffic.sh 20

# remove everything, in reverse order
bash scripts/rollback.sh

Auth is the operator's own user credentials via a bearer token; no service-account key is stored. Deterministic IDs mean the alerts and dashboard can reference the SLO resource paths as literals, which is what makes apply.sh safe to re-run.

8 · Gotchas worth knowing

Four things that each cost a failed apply, written down so the next person skips them:

  • Dashboards live on a different API version. Services, SLOs, alert policies and channels are Monitoring v3; dashboards are v1 only. A dashboard call to v3 returns an HTML 404, not JSON.
  • The response-code label is an integer. On proxy/response_count, response_code is INT64, so starts_with("5") is rejected — "function restrictions are only allowed for string type." Use a numeric range: >=500 and <600. Dashboards do not validate filters at create time, so a bad one there fails silently at render; the SLO fails loudly.
  • The CLI could not do the job; the API could. The installed gcloud had no subcommands for SLOs, services, channels, or Apigee env-groups. Everything was done over REST instead — one uniform, portable path.
  • Old shell, no associative arrays. macOS ships Bash 3.2, which has no declare -A. The traffic seeder loops a plain list and resolves the env-group hostname over REST.

9 · Caveats & next steps

  • Verify the email channel. It came back with an unspecified verification status. Until it is confirmed, the burn-rate alerts have nowhere to page.
  • Decide on the latency target. See section 6 — the 300 ms objective is honest but tight against the real distribution. Widen it, or keep it and treat the tail as a backend task.
  • Idle proxies read "no data" on the by-proxy panels until traffic flows. The seed lit up the proxies whose rejection happens inside the proxy; the ones gated by an API key before dispatch need a real key to register, which was left out of scope.
  • The SLO window is warming up. Both SLOs compute forward over a 28-day window that is mostly empty today, so the budget readouts will settle as the window fills. The 92.7% figure is independent of this — it is measured straight off the distribution.
